# KV_FRONTIER — the O(1) memory claim vs quantized / evicted KV caches

> One page. Companion artifacts: `benchmarks/results/kv_frontier.md` (full
> grid), `benchmarks/results/kv_frontier_ledger.json` (machine-readable),
> regenerated by `python benchmarks/kv_frontier.py`. Evidence-base rows live
> in RESULTS.md / BENCHMARKS.md; this page explains **why the account has to
> be run proactively at all.**

## 1. Why this account must be computed before a reviewer computes it

The repo's O(1) headline — ARR carried state flat at 0.381 MB vs a KV cache,
1008× @128k / 8063× @1M — was measured against a **fp16, GQA=1** KV cache.
That is the *weakest* opposing configuration. The KV-compression literature
has spent 2024–2026 attacking exactly that baseline, so any reviewer's first
question is "…compared to 2-bit KV? GQA? sink+window eviction?". Public
anchors, all peer-reviewed:

| Method | What it does | Public number | Source |
|---|---|---|---|
| **KIVI** | 2-bit *asymmetric* KV quant (per-channel K, per-token V) | up to **2.35× / 3.47×** decode throughput (Llama-2-7B/13B chat) | Liu et al., NeurIPS 2024, [arXiv:2402.02750](https://arxiv.org/abs/2402.02750) |
| **KVQuant** | 4-bit NF4 + fp16 outliers | **million-token** contexts on a single GPU | Hooper et al., NeurIPS 2024, [arXiv:2406.17570](https://arxiv.org/abs/2406.17570) |
| **NVFP4** | 4-bit floating format (E2M1 + FP8 block scales), Blackwell KV path | — (represented by our 4-bit row) | NVIDIA/TRT-LLM format spec |
| **StreamingLLM** | sink(4) + sliding window eviction | up to **22.2×** per-token speedup vs window-recomputation, constant cache | Xiao et al., ICLR 2024, [arXiv:2309.17453](https://arxiv.org/abs/2309.17453) |
| **SnapKV** | observation-driven KV eviction | **3.6×** generation speed, **8.2×** memory efficiency | Li et al., NeurIPS 2024, [arXiv:2404.14469](https://arxiv.org/abs/2404.14469) |

If compression shrinks the O(T) line by 8×, does the O(1) claim survive?
The honest answer requires **byte-exact accounting on both sides**, not
rhetoric — and it must weight *our* hybrid's KV the same way we weight the
opponent's.

## 2. The method (everything re-derivable from one command)

* **KV side — pure analytic integers.** Base storage
  `2·L·n_kv·d_head·T·bits` bit-packed; bits<16 adds KIVI-style asymmetric
  metadata (per-token fp16 V scales `L·n_kv·T·2` B + per-channel fp16 K
  scales `L·n_kv·d_head·2` B; zero-points fold away at 0 B). Eviction caps
  the cached length at `sink(4)+window` → constant beyond the cap.
  GQA sensitivity at n_kv ∈ {1, 8} (matched model has 13 query heads;
  n_kv=1 is the smallest honest KV — i.e. the *hardest* opponent for us).
* **ARR side — measured, never hand-copied.** The flat snapshot-byte sum is
  loaded from `benchmarks/results/decode.json`, freshly produced by
  `benchmarks/scaling_comparison.py --mode decode` at the same geometry the
  analytic side uses (L=12, d_head=64, read from the JSON itself).
* **Hybrid honesty row.** The M-series hybrid contains attention too, so its
  carried state is charged `kv@2bit + measured liquid stream` — the ledger
  never applies compression only to the opponent.
* **Crossover T\*** = smallest context at which the config's carried bytes
  **exceed** the ARR state — the lower bound of the interval where ARR is
  strictly smaller. Solved by exact binary search over the monotone byte
  curve; unit-tested in `tests/test_kv_frontier.py`.

Validation anchor: the ledger reproduces the published fp16/GQA=1 numbers
exactly (1.5 MB @512, 3072 MB @1M, **1007.9× @128k, 8063.0× @1M**) before
extending to the compressed frontier.

## 3. The verdict (condensed; full grid in the artifacts)

| opponent (non-evicted KV) | ARR smaller for | config/ARR @128k | @1M |
|---|---|---|---|
| fp16 GQA=1 (the old baseline) | T ≥ 131 | 1007.9× | 8063.0× |
| **2-bit GQA=8 (strongest compression)** | **T ≥ 119** | **1070.9×** | **8567.0×** |
| 2-bit GQA=1 | T ≥ 976 | 133.9× | 1070.9× |
| 4-bit GQA=1 / 8 | T ≥ 503 / 62 | 259.9× / 2078.8× | 2078.8× / 16630.0× |
| 8-bit GQA=1 / 8 | T ≥ 256 / 32 | 511.8× / 4094.5× | 4094.5× / 32756.0× |
| fp16 GQA=8 | T ≥ 17 | 8063.0× | 64504.0× |

**Eviction is the real frontier, not quantization.** sink(4)+window:

| eviction config | constant memory | vs ARR 0.381 MB |
|---|---|---|
| w=4096, any bits/GQA tested | 1.60–96.1 MB | ARR smaller ∀ T ≥ T* (4.2×–252×) |
| w=512, 4-bit GQA=1 | 0.391 MB | ARR smaller by **1.03× only** — a de facto tie |
| **w=512, 2-bit GQA=1** | **0.202 MB** | **ARR never smaller (0.53×) — the claim's honest loss** |

So: against every *non-evicted* configuration — including the strongest
2-bit+GQA=8 compression — the ARR state is smaller throughout the common
range (crossover at 17–976 tokens ≪ 128k) and the advantage **grows**
with context (8,567× @1M vs 2-bit GQA=8; 64,504× vs fp16 GQA=8). Against
*small-window eviction + 2-bit*, ARR loses on pure carried bytes at every
context length. That combination is exactly where the capability account
decides the comparison (§5).

## 4. Honest corrections this forces (mirrored in RESULTS.md)

1. **Below T\*≈0.1–1k tokens, the compressed KV cache is smaller than the
   ARR state.** The O(1) claim is a *long-context* claim; at short context a
   0.381 MB state is simply bigger than a few hundred tokens of 2-bit KV.
2. **ARR is not the minimum carried-state configuration.**
   sink(4)+window(512) eviction at 2-bit GQA=1 carries 0.202 MB flat —
   0.53× the ARR state — for all T. "Smallest possible streaming memory"
   is **not** ours to claim; "smallest *without discarding context*" is.
3. **4-bit + window(512) + GQA=1 is a de facto tie** (1.03×) — report it as
   a tie, not a win.

## 5. Memory is not capability (the joint footnote)

Eviction wins the byte account by discarding tokens; the repo has already
measured what that costs: attention is structurally **0.000** on cross-window
associative recall while the fast-weight state scores **0.56** (RESULTS.md,
"Cross-window associative recall" — 3 seeds; removing the fast-weight matrix
collapses it 0.553 → 0.008). A binding evicted past the window is gone; a
binding written into the state is not. The honest joint statement is two
accounts side by side, not one:

> *Bytes:* eviction+2-bit can undercut the ARR state everywhere.
> *Retrieval:* it does so with structurally-zero out-of-window recall,
> where the fast-weight state retains 0.56.

The reverse honesty also holds: ARR's own quality beyond its 512-token
training length is unproven (RESULTS.md out-of-window nulls), so neither
side gets to borrow quality from the other's ledger.

## 6. Which real tasks the eviction concession actually hits

window(512) is a few hundred words — under one page of text. Whether the
0.202-vs-0.381 MB sacrifice matters is decided by one question: is
anything ever needed from beyond the window?

* **Fatal for eviction** (structural 0 vs fast-weight 0.56): long-document
  QA past the first page; persistent per-user memory across sessions;
  repo-scale coding (a signature defined 50k tokens earlier); streaming
  monitoring that must correlate an early anomaly with now. What these
  share: retrieving a discrete fact whose location is outside the window.
* **Cost ≈ 0**: in-window chat, local rewriting, per-segment translation,
  map-reduce summarization, single-call classification — and any system
  with an external retrieval loop (RAG) that re-injects evicted content;
  there eviction's byte win is real and its capability cost is covered.

Boundary honesty: the proven edge is discrete key→value associative
recall, NOT long-context LM — needle@4096 is 0.000 for *both* (base RoPE
limit) and ARR's own out-of-window LM is a null (RESULTS.md). The 0.381 MB
is irreplaceable exactly and only on the first class of tasks — which is
why the external claim is scoped to "smallest carried state *without
discarding context*".

## 7. Reproduce

```bash
# 1) measured ARR flat line (CPU, ~25 min for the full 512→1M ladder):
python benchmarks/scaling_comparison.py --mode decode \
  --profile_lens 512,2048,8192,32768,131072,524288,1048576 \
  --out_dir benchmarks/results
# 2) the frontier ledger (seconds):
python benchmarks/kv_frontier.py            # -> results/kv_frontier.{md,json}
# 3) the gates:
python -m pytest tests/test_kv_frontier.py -q
```
