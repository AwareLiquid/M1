# ADJ-009 · 2026-09-07 · 绿 PR 队列批次整合纪律(合并窗口制)

**调整**:常设"合并窗口整合制"——绿 PR 队列(不含 draft/停泊/待补件)>3 时,
按语义聚类(工程/文档)组成批次整合分支送审,管理员一次审核合并一批,
合入后由执行方关闭被承载的旧 PR(对齐 #31→#32 模式)。聚类以"文件交集 +
依赖链"为准:同文件或依赖链上的 PR 必须同簇;不同簇之间要求零文件交集。

**根因证据**:2026-09-06/07 两天的并行产出使队列堆积至 11 个开放 PR
(8 个全绿待审),单一管理员审核成为吞吐瓶颈;堆叠链(#33→#35、#32→#34/#37)
使逐个合并需要 3 次 squash 后 rebase。整合后队列回落至 3 个(均有意持有)。

**验证**:批次4a(工程+治理底座:#32/#34/#36/#37/#39)与批次4b(路线图:
#33/#35/#38)两簇各自 CI 全绿、簇间零文件交集(comm 校验);8 个旧 PR 经
merge-base --is-ancestor 逐个校验承载后立即关闭(2026-09-07 已执行),
此后队列常态 ≤3(仅 #25 待补件/#22 draft/#2 停泊)。

**追记(2026-09-07,owner 纠正)**:初稿写"合入后关闭旧 PR",执行口径修正为
**承载即关**——整合分支创建且祖先关系校验通过即关闭,不等合入。原因:
等合入会让被承载的旧 PR 在队列里反复堆积(owner 两次纠正同一行为:
#31→#32 批次、批次4 整合),与整合制的去堆积目的自相矛盾。旧分支保留,
整合 PR 被否决时可重开,无内容丢失风险。
